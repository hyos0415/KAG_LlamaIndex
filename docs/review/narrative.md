## 2. 감사가 이 서사에 던지는 문제 (미해결)

### 2.1 "한계 발견"의 내용이 바뀐다

handoff 는 기존 프로젝트의 한계를 **"스키마를 늦게 붙였다"** 로 요약한다.
그런데 감사 결과 더 앞선 층이 있었다 `[A §1.4]`:

**응용 경로가 그래프를 아예 저장하지 않았다.** `app/**` 에 `persist` 호출 0건이고
그래프에 들어가는 청크는 2~5개다. README 가 KG 도입 근거로 내세운
"1월 기사 + 3월 기사 연결"은 정규화나 코퍼스 규모 이전에 **코드 구조상 불가능**했다.

→ 서사 선택지 (미정):
  - (a) "스키마가 늦었다"를 유지하고 이 층은 각주로
  - (b) "그래프를 만들었지만 쓰지 않았다"를 1차 한계로, 스키마를 2차로
  - (c) 두 층을 분리해 "설계 층과 구현 층이 각각 실패했다"

(b)/(c) 는 더 정직하지만 더 아프다. **어느 쪽으로 쓸지는 사람이 정한다.**

### 2.2 "정규화가 답이 아니었다"를 어디에 둘까 `[X D2]`

이 저장소의 진단은 negative result 다 — 규모·관계 정규화·엔티티 정규화가 모두 기각되고
자유 스키마 추출기가 원인으로 남았다. handoff §2.1 은 정규화 부재를 개선 가능한
결함으로 나열하는데, 실측은 정규화의 상한이 4.5%라고 말한다.

→ 이건 서사에서 **약점이 아니라 소거법의 성과**로 쓸 수 있다. 다만 그렇게 쓰려면
handoff §2.1 을 정정해야 한다 (`spec/cowork` 브랜치 Q2).

### 2.3 이관 자산이 코드가 아니라는 것 `[X C2]`

두 감사가 독립적으로 도달했다. 포트폴리오에서 "무엇을 만들었나"보다
"어떻게 틀렸음을 알아냈나"가 산출물이 되는 구조다.

→ 서사 후보 (미정): 사전 등록이 3번 정정된 이력(CONTEXT 발견 16)을 숨기지 않고
   전면에 두는 것. "기준이 틀렸는데 지목 가능했다"가 방법론 주장이 된다.

## 3. 미정

- 발표 대상 (채용 / 학회 / 블로그)에 따라 위 선택이 갈린다
- negative result 를 어느 비중으로 둘지
- 세 도구(Claude Code / Codex / GPT)의 교차 검증 과정 자체를 서사에 넣을지
