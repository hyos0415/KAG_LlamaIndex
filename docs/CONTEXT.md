## 1. 이 프로젝트가 무엇인가

매일경제 기사를 수집해서, 기자 초안의 객관성과 관점 신규성을 검증하는 시스템입니다.

핵심 발상: 기사에서 `(주체, 관계, 대상)` 트리플을 뽑아 그래프로 쌓으면, 여러 기사에 흩어진 사실을 이어붙일 수 있다. A사→B사 투자가 1월 기사에, B사→C사 납품이 3월 기사에 있으면, 어느 기사에도 없는 A-C 간접 관계가 그래프에서 도출된다. 문서 검색으로는 불가능한 연산이다.

스택: Airflow ETL · PostgreSQL · Elasticsearch · ChromaDB · Neo4j · LlamaIndex PropertyGraphIndex · LangGraph

레포: `~/Desktop/mk_news/news-arena` (외곽의 `mk_news`는 커밋 없는 껍데기 git — 건드리지 말 것)

1. **규모 억제 결정이 KG 작동 조건을 차단했다** — 수집 40건 중 5건만 색인.

   관측된 44개 컴포넌트가 그 결과다.

14. **엔티티와 사건이 구분되지 않는다** — v0' 엔티티 목록에 `정성국 의원직 사퇴`, `한동훈 제명 재고`, `노점 영업중단`, `노점 위생 논란`, `화재 원인` 같은 노드가 존재한다. 이들은 엔티티가 아니라 사건·속성이며, (정성국, 사퇴하다, 의원직) 형태의 관계로 표현되어야 할 것이 노드 하나로 뭉쳤다.
    사건 노드는 해당 문장에만 존재하므로 다른 문서와 결코 연결되지 않는다. 그래프 조각화의 독립적 원인이며, 발견 5(표기 변형)와는 다른 문제다.
    발견 13의 42쌍 후보 목록에 이 유형이 섞여 있으므로, substring 기준 자동 병합은 표기 변형과 사건 노드를 함께 합쳐 그래프를 왜곡한다.

## 4. 결론 — 왜 KG 이점이 발생하지 않았나

기술 선택은 타당했습니다. 문제는 **부품 사이가 연결되지 않은 것**입니다.

```

정규화가 없어 그 5건조차 44조각(v0' 재측정 33조각)으로 쪼개졌고
Neo4j는 경로 밖에 있었고
그래프 결과는 최종 리포트에 문자열로 덧붙여졌다

→ 지식그래프의 이점이 발생할 조건 자체가 갖춰지지 않았다
```

이것은 실험으로 답할 문제가 아니라 구조로 이미 확인된 사실입니다.

## 6. 현재 유효한 계획

### 검증할 가설

그래프가 44조각인 원인이 둘 중 무엇인가.

```
가설 A  기사가 5건뿐이라 이어질 게 없다      → 규모 문제
가설 B  같은 대상이 다른 이름으로 저장됐다   → 정규화 문제
```

### v0 강등과 v0' 신설

`storage_claude/` 생성 스크립트가 레포에 없어 v0는 재현 불가하다.
따라서 v0 vs v0' 차이로 모델 드리프트를 특정할 수 없다
(원인이 드리프트인지 코드 경로 차이인지 구별 불가).

```
v0   2026-02 측정값. 역사적 참고값. 비교 기준으로 사용하지 않음
v0'  현재 코드로 재측정한 5건. 실제 기준선
v1~  v0'와 동일 코드 경로
```

### 측정 지점

```
v0   2026-02 측정값 (5건, 정규화 없음)      ← 역사적 참고값. 비교 기준 아님
v0'  5건 색인, 정규화 없음, 현재 코드/모델  ← 실제 기준선
v1   40건 색인, 정규화 없음                 ← v0'와 동일 코드 경로
v2   40건 색인, 정규화 적용                 ← 가설 B 검증
◆ 게이트: v1→v2 효과 크기로 v3/v4 진행 여부 결정
v3   200건 색인, 정규화 없음                ← 가설 A 검증
v4   200건 색인, 정규화 적용                ← 상호작용
```

v0'→v1은 규모 축의 두 번째 관측점이 되어, 게이트 판단의 외삽 근거로 사용됩니다.

**v1→v2를 먼저 하고 게이트에서 판단합니다.** 정규화 효과가 40건에서 이미 크면 200건 수집이 결론을 바꾸지 않으므로, 크롤러 개조(2~4시간)를 하지 않습니다.

예상 상호작용: 규모가 커지면 별칭 충돌이 늘어 **정규화 효과가 규모에 따라 커질 것**. 실증되면 "데이터를 더 모으는 게 답이 아니었다"가 헤드라인이 됩니다.

단 정규화 자체도 규모에 따라 어려워진다. `대통령` → `이재명` 병합은 5건 코퍼스에서만 성립하며, 200건에서는 다른 인물이 등장해 오병합이 된다. 규모가 커지면 정규화의 필요성과 난이도가 함께 증가한다.

### 지표 — 전부 결정론적

LLM judge, 루브릭, 블라인드 평가가 필요 없습니다. 그래프 쿼리로 나오는 숫자라 정답이 논쟁되지 않습니다.

**규모가 다른 지점을 비교하므로 절대 개수는 쓸 수 없습니다. 반드시 비율로 정의합니다.**

| 지표 | 정의 | v0' (5건, 실제 기준선) | v0 (참고, 해석 안 함) | 방향 |
|---|---|---|---|---|
| `components_per_doc` | 연결 컴포넌트 수 / 색인 문서 수 | 33 / 5 = 6.6 | 44 / 5 = 8.8 | 낮을수록 좋음 |
| `bridges_per_doc` | 브릿지 엔티티 수 / 색인 문서 수 | 2 / 5 = 0.4 | 3 / 5 = 0.6 | 높을수록 좋음 |
| `cross_doc_path_ratio` | 교차문서 경로 / 전체 hop≥2 경로 | 27 / 213 = 0.127 | 33 / 186 = 0.177 | 높을수록 좋음 |
| `rel_type_ratio` | 관계 타입 수 / 관계 수 | 73 / 94 = 0.777 | 80 / 92 = 0.870 | 낮을수록 좋음 |
| `parse_failure_ratio` | placeholder 노드 / 전체 엔티티 | 0 / 118 = 0.000 | 2 / 134 = 0.015 | 낮을수록 좋음 |
| `isolated_doc_ratio` | 고립 문서 / 색인 문서 | 2 / 5 = 0.4 | 2 / 5 = 0.4 | 낮을수록 좋음 |
| `entities_per_doc` | 고유 엔티티 수 / 색인 문서 수 | 118 / 5 = 23.6 | 134 / 5 = 26.8 | 코퍼스 증가 시 하락해야 정상 |

**정정 (2026-08-01)**: 기존 표의 rel_type_ratio 16/18=0.89는 Neo4j 데모 데이터(에디슨모터스 판결, 27노드/18관계) 수치였고 같은 행의 다른 지표는 property_graph_store.json 수치였다. 두 그래프가 섞여 있었다. v0 재계산값(전부 property_graph_store.json 기준)은 rel_type_ratio 80/92=0.870이다.

v0'→v1 에서 이 값이 유지되면 엔티티 재사용이 없다는 뜻이며,
정규화 부재가 확증된다. v1→v2 정규화 효과의 예측치가 된다.

**지표 정의를 실행 후에 바꾸지 마세요.** 사후 조정이 됩니다.

### 게이트 판정 기준 (확정 — §8 미정 3 해결)

기준선: v0' 실측 — components_per_doc 6.6, entities_per_doc 23.6
v0(8.8 / 26.8)는 역사적 참고값이며 게이트 판정에 사용하지 않는다.

이 지표는 엔티티 재사용이 없으면 문서 수와 무관하게 값이 유지된다.
5건 → 40건에서 각 기사의 상대 문서가 4개 → 39개로 약 10배 늘어나므로,
이름이 통일돼 있다면 값이 유의미하게 하락해야 한다.

**주 지표: `components_per_doc`의 v0' 대비 감소율**

| 값 | 판정 |
|---|---|
| ≤ 20% 감소 | 무변화. 수집 중단, 정규화로 전환 |
| 20~55% 감소 | 보류. v2 결과로 판단 |
| ≥ 55% 감소 | 규모 유효. 200건 수집 진행 |

(v0'=8.8 가정 시 각각 7.0 / 4.0 에 해당. **실측 v0'=6.6 기준 절대값: ≥5.28 무변화 / 2.97~5.28 보류 / ≤2.97 규모 유효**)

**확인 지표: `entities_per_doc`의 v0' 대비 감소율**

| 값 | 판정 |
|---|---|
| < 10% 감소 | 재사용 없음. 이름 문제 확정 |
| ≥ 33% 감소 | 재사용 발생 |

(v0'=26.8 가정 시 각각 24 / 18 에 해당. **실측 v0'=23.6 기준 절대값: ≥21.24 재사용 없음 / ≤15.81 재사용 발생**)

**해석 규칙 (v1 실행 전 사전 등록)**

v0→v0' 관측에서 components_per_doc은 개선(8.8→6.6)됐으나 cross_doc_path_ratio(0.177→0.127)와 브릿지 수(3→2)는 악화됐다. 엔티티 134→118, 관계 92→94이므로, 문서 내부에서 엔티티가 통합되어 서브그래프가 촘촘해진 결과이며 문서 간 연결이 늘어난 것이 아니다.

따라서 components_per_doc은 두 요인이 섞인 지표다.
- (a) 문서 내 엔티티 통합 — 추출 품질이 좌우. 규모와 무관
- (b) 문서 간 연결 — 이번 실험의 검증 대상

판정 규칙:
- components_per_doc 하락 + cross_doc_path_ratio·bridges_per_doc 개선 → 규모 유효. 게이트 표대로 판정
- components_per_doc 하락 + 위 둘 미개선 → 문서 내 통합에 불과. 규모 효과 아님. '무변화'로 처리
- components_per_doc만 악화 → 계산 오류 의심. 진행 중단

**정정 (v1 실행 후)**: 위 규칙은 cross_doc_path_ratio와 bridges_per_doc을 규모 효과의 확인 지표로 삼았으나, 이 두 지표는 조합론적으로 문서 수에 따라 증가한다. 문서 내 경로는 N에 비례하지만 교차 경로는 문서 쌍 수에 비례하므로, 이름 재사용률이 개선되지 않아도 비율이 상승한다. v1 실측(0.127 → 0.721, +468%)이 이 인플레이션의 예다.

따라서 규모 효과의 유효한 지표는 entities_per_doc 하나이며, 이는 문서 수 증가에 따른 기계적 상승을 받지 않는다. v1 판정은 entities_per_doc −2.0%와 섹션별 부분집합에서의 악화에 근거하며, cross_doc_path_ratio 개선은 근거로 사용하지 않았다.

엇갈릴 경우 `entities_per_doc` 우선.
섬(컴포넌트) 감소 + 엔티티 유지 → 계산 오류 의심, 진행 중단.

**교란 통제**: 현재 40건은 9개 섹션에 흩어진 이틀치 일반 뉴스이므로,
이름이 통일돼도 주제 무관으로 안 붙을 수 있다.
전체 40건과 별도로 섹션별 부분집합(증권 12건, 사회 10건)에서도
같은 지표를 산출한다. 증권 12건에서도 무변화면 주제 무관 가설이
배제되고 이름 문제가 확정된다. 추가 호출 없음.

이 기준은 v1 측정 전에 확정되었으며 결과를 보고 수정하지 않는다.

### LLM 설정 (확정 — §8 미정 5 해결)

트리플 추출에 사용할 LLM 설정을 v0'~v4 전 구간 고정한다.

| 항목 | 값 |

근거: v0 측정 당시 설정을 유지하려 했으나 claude-sonnet-4-0 폐기로 불가. 후속 세대 중 핀 고정 스냅샷을 선택했다. 외부 제약에 의한 강제 변경이다.

**주의**: `claude-sonnet-4-5-20250929`는 핀 고정 스냅샷이므로 실행 중 이동하지 않는다. 다만 폐기 가능성은 남으므로 모든 실행에서 API 응답의 실제 모델 ID를 기록한다.

**갱신 (2026-08-01)**: `claude-sonnet-4-0`으로 Stage 1 실행 시 API가 404(model not found)를 반환 — 별칭이 이동한 정도가 아니라 완전히 폐기됨을 확인(`client.models.list()`로 접근 가능한 모델 목록에 부재). v0가 그 별칭으로 측정된 뒤 현재 사이에 세대 자체가 바뀌었다는 뜻이며, 이는 v0가 참고값으로만 남고 v0'가 실제 기준선이 되어야 하는 이유를 한 번 더 확증한다. 고정값을 `claude-sonnet-4-5-20250929`로 갱신한다.

파이프라인에 LLM이 두 개 있다. 위 고정 설정은 트리플 추출용이며,
`enricher.py`의 메타데이터 추출 LLM과 `SemanticSplitter`의 embed_model은
별도로 고정해야 한다. 고정하지 않으면 메타데이터 변동이 트리플 추출 입력에
섞여 규모 효과와 분리되지 않는다.

### 추출 코드 경로 (확정 — §8 미정 6 해결)

트리플 추출 + 그래프 구축은 `jit_builder.py`(`JITGraphAnalyzer.build_and_analyze`)
경로를 v0'~v4 전 구간 고정한다. `knowledge_graph.py`(`sync_to_neo4j`)는 사용하지 않는다.

근거:
- `sync_to_neo4j`는 `Neo4jGraphStore`를 하드코딩하므로 로컬 JSON 산출이 구조적으로 불가능 (§8 미정 4의 "로컬 JSON 유지" 결정과 상충)
- `build_and_analyze`의 기본값(`property_graph_store` 미지정 → `SimplePropertyGraphStore`)이 `storage_claude/property_graph_store.json`의 형식과 일치

**주의**: `build_and_analyze`를 통째로 호출하지 않는다. 그래프 구축 단계(문서화 → 추출기 → `PropertyGraphIndex.from_documents`)까지만 재사용하고, 이후의 육각형 리포트 쿼리 단계(`query_engine.query()`)는 포함하지 않는다 — 트리플 추출과 무관한 LLM 호출이 추가되기 때문.

### 2단계 분리 (Stage 1 / Stage 2)

```
Stage 1  청킹 + 메타데이터 추출 → tests/fixtures/chunks_40.json (40건, 1회만)
```

목적: 메타데이터 추출 LLM과 embed_model의 변동을 v0'~v4 전 구간에서 제거한다.
남는 변동 요인은 트리플 추출 하나뿐이다.

- 모델: `claude-sonnet-4-5-20250929` — 단, Stage 1에 계측이 없어 API 응답 기준 실측이 아니라 추론이다. 근거: 첫 실행이 `claude-sonnet-4-0`으로 첫 기사에서 404 실패하여 산출물이 없었고, 모델 갱신 후 재실행이 40건 전부를 생성했다. 모델 혼입은 구조적으로 불가능하다.
- 결과: 40건 → 86청크 (2청크 34건, 3청크 6건)
- 정합성: v0 대상 5건이 2/2/2/2/2 = 10청크로 v0와 일치. embed_model이 OpenAI라 Anthropic 모델 교체의 영향을 받지 않았음을 시사한다. (기록만. 진행 조건으로 사용하지 않는다)

**트리플 캐싱**: v0'와 v1이 같은 10청크를 두 번 추출하면, v0'→v1 차이에 "문서 추가 효과"와 "동일 청크 재추출 노이즈"가 섞인다. `SimpleLLMPathExtractor`는 노드 단위 독립 처리이므로 node_id로 캐싱이 유효하다.
- `experiments/shared/triple_cache.json`에 node_id → 추출된 트리플 목록 저장
- Stage 2 실행 시 캐시에 있는 node_id는 추출을 건너뛰고 재사용
- 캐시 히트/미스 수를 `run_metrics.json`에 기록
- `--no-cache` 플래그로 우회 가능 (검증용)

### 정규화 작업 내용 (LLM 호출 0)

결정론적 후처리입니다. 추출된 트리플에 사후 적용하므로 추출을 다시 하지 않습니다.

**엔티티** — 별칭 사전 + 표기 정규화

`삼성전자 · 삼성 · 삼성전자(005930)` 예시는 v0' 데이터에 해당 엔티티가 전혀 없어 미검증 상태로 삭제한다(관계 예시와 같은 문제 — 실제 있는지 확인 안 된 가상 예시였음).

실제 v0'에서 검증된 예시(발견 13, 위 42쌍 후보 목록 참고):
```
이재명 · 이재명 대통령 · 대통령      → 이재명   (v0'에서 실제로 3개 별개 노드로 분화됨을 확인)
```

**관계** — 한국어 활용형 정규화가 핵심

기존에 적어뒀던 예시(선고/선고했다/판단/피해입었다/특징/모습/PREDICATE)는 **Neo4j 데모 데이터**(에디슨모터스 판결, 실제 기사와 무관)에서 온 것이었고 v0' 실제 데이터 존재 여부가 확인된 바 없어 삭제한다. 실제 v0' 73종 전체 빈도 목록은 `tests/fixtures/baseline_v0prime.json`의 `relation_type_freq` 참고.

아래는 실제 데이터에서 고른 **후보 제시일 뿐 확정이 아니다** — 온톨로지 목표 개수·최종 목록은 §8 미정 2(사람이 결정).

활용형 변형 후보 (같은 개념의 활용형/조사 차이로 보임):
```
촉구 · 촉구했다
직위 · 직위는                 (조사 차이)
상태 · 상태는                 (조사 차이)
발생 · 발생 장소 · 발생 날짜 · 발생 위치 · 발생 층 · 화재 발생 · 발생한 사건
사망 · 사망 원인 · 사망 장소 · 사망 후 경과
개최 회차 · 개최 장소 · 개최 시작
질책 · 질책했던 곳
Died in · Died from            (영문, 전치사 차이)
```

언어 혼용 후보 (한국어 기사인데 영문 라벨 — 별도 이슈, 활용형과는 다른 문제):
```
Is · Died in · Died from · Member of · Spouse of · Married · Divorced in
```
(전부 구준엽/서희원 기사(11952002) 한 건에서 나옴 — 특정 기사·주제에 편중된 현상인지 표본이 더 필요)

저정보/무의미 타입 후보 (검토 필요, 확정 아님):
```
조회수 · 행위 · 포함
```

관계 온톨로지 목표 목록은 **실제 등장 빈도에서 유도**합니다. 상상해서 만들지 마세요.
버려진 트리플 비율을 로그로 남기세요. 20% 초과면 온톨로지가 너무 좁습니다.

### 200건 수집 (게이트 통과 시에만)

(참고) 40건 색인(v1)은 버그 수정이 아니라 기존 인덱싱 스크립트 재실행만으로 가능합니다 — §3 발견 1 참고.

- 크롤러(`app/etl/extractor.py`)는 BeautifulSoup 기반이므로 **진입점만 바꾸면** 과거 기사 수집 가능. 본문 파서는 재사용
- RSS 피드 → 섹션 목록 페이지 페이지네이션
- `robots.txt` 확인, 요청 간 1초 이상 지연
- **증권·기업 섹션 최근 2~3개월치**. 무작위 수집은 현재 40건과 같은 실패를 반복함 (엔티티 재등장률이 관건)
- 인수합병·규제 후속보도가 섞이면 상태 변화(검토→철회)가 잡혀 후속 작업의 재료가 됨

## 7. 절대 금지

1. **측정 전에 제거하지 않는다.** 미검증 가설로 코드를 삭제하지 말 것
2. **한 번에 하나만 바꾼다.** v1→v2에서 정규화 외의 것을 건드리면 효과가 분리되지 않음
3. **베이스라인을 덮어쓰지 않는다.** `tests/fixtures/baseline_v*.json`은 append만
4. **지표 정의를 실행 후 변경하지 않는다**
5. **범위 밖 리팩토링 금지.** 발견 사항은 `docs/found-issues.md`에 기록만 하고 고치지 말 것
6. **ETL/DAG를 임의로 실행하지 않는다.** 색인은 명시적 지시가 있을 때만
7. **`docs/archive/` 를 참조하지 않는다.** 폐기된 설계
8. **미정 사항을 임의로 정하지 않는다.** §8 참조. 물어볼 것
9. **Stage 1 산출물(`tests/fixtures/chunks_40.json`)을 덮어쓰지 않는다.** v0'~v4 전 구간의 공유 입력이므로 변경 시 모든 측정 지점이 무효가 된다.
