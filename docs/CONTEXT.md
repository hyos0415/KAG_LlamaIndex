## 1. 이 프로젝트가 무엇인가

매일경제 기사를 수집해서, 기자 초안의 객관성과 관점 신규성을 검증하는 시스템입니다.

핵심 발상: 기사에서 `(주체, 관계, 대상)` 트리플을 뽑아 그래프로 쌓으면, 여러 기사에 흩어진 사실을 이어붙일 수 있다. A사→B사 투자가 1월 기사에, B사→C사 납품이 3월 기사에 있으면, 어느 기사에도 없는 A-C 간접 관계가 그래프에서 도출된다. 문서 검색으로는 불가능한 연산이다.

스택: Airflow ETL · PostgreSQL · Elasticsearch · ChromaDB · Neo4j · LlamaIndex PropertyGraphIndex · LangGraph

레포: `~/Desktop/mk_news/news-arena` (외곽의 `mk_news`는 커밋 없는 껍데기 git — 건드리지 말 것)

## 2. 지금 하고 있는 일

**기능 개발이 아니라 진단과 개선 측정입니다.**

이 프로젝트는 완성된 뒤 방치돼 있었고, 지식그래프를 도입한 근거("LLM 응답이 일관되지 않다")가 한 번도 검증되지 않았다는 문제의식에서 재개했습니다.

현황 조사를 마쳤고(§3), 원래 계획했던 그래프 순회 실험은 데이터 부족으로 불가 판정이 났습니다(§5). 현재 유효한 계획은 §6입니다.

## 3. 현황 조사 결과 (실측, 2026-08-01)

상세: `docs/00-baseline-survey.md`

### 파이프라인 5단계 중 4단계에 문제

| 단계 | 상태 | 실측 |
|---|---|---|
| RSS 수집 | 정상 | 기사 40건 (01-26에 6건, 02-03에 34건) |
| 색인 | **문제** | 5건만 반영. 35건 누락 |
| 트리플 추출 | **문제** | 관계 18건에 타입 16종 |
| 그래프 저장 | **문제** | Neo4j 미연결. 실제 저장소는 로컬 JSON |
| 리포트 생성 | **문제** | f-string 결합. 그래프가 추론에 개입 못 함 |

### 발견 8개

1. **규모 억제 결정이 KG 작동 조건을 차단했다** — 수집 40건 중 5건만 색인.
   이는 버그가 아니라 '그래프가 방대해질 것'이라는 우려에 따른 의도적 표본 추출 결정이었다.
   그러나 교차 문서 경로는 같은 엔티티가 여러 기사에 반복 등장해야 생기므로,
   코퍼스 축소가 지식그래프의 작동 조건 자체를 제거했다.
   관측된 44개 컴포넌트가 그 결과다.

   규모 우려는 실측 기준 근거가 부족했다. 5건 → 엔티티 134개 / 544KB 이므로
   선형 외삽 시 200건에서도 약 5,400 엔티티 / 20MB 수준이며,
   Neo4j 및 로컬 저장소가 자릿수 여유를 두고 처리 가능한 규모다.
2. **Neo4j가 실제 경로에 없었다** — 27노드/18관계, 수집 기사와 무관한 데모 데이터(에디슨모터스 판결), 관계 프로퍼티 전부 `{}`로 출처 추적 불가
3. **실제 동작한 그래프는 `storage_claude/property_graph_store.json`** — 134 엔티티, 92 트리플, provenance 완비 (`news_id`, `pub_date`, `triplet_source_id`)
4. **그래프가 44조각** — 엔티티 134개 / 연결 컴포넌트 44개. 기사별 별 모양 서브그래프
5. **엔티티 정규화 부재** — `이재명` ≠ `이재명 대통령` 별개 노드
6. **관계 타입 폭발** — 타입/관계 비율 0.89. `선고`·`선고했다`·`선고받았다` 별개 타입. `특징`·`모습` 같은 무의미 타입 존재
7. **추출 파싱 실패** — `Subject`/`Object` placeholder 노드 잔존 (`SimpleLLMPathExtractor` fallback)
8. **브릿지가 3개뿐** — `이재명`, `이재명 대통령`, `국민의힘`. 대표 경로 5개 전부 이재명 경유. 5개 기사 중 2개 완전 고립

### 기타

- 추출기: `SimpleLLMPathExtractor` (자유 스키마 — 관계 타입을 LLM이 자유 결정)
- `llama-index-core==0.14.13`, uv 환경, `.venv` 존재
- `neo4j_data`는 bind mount (named volume 아님) — 4.2M 로컬 잔존
- `chroma_db` 31M, `rag_eval_results.csv` 95행
- compose에 `postgres_data`/`redis_data` 선언은 있으나 서비스 없음 (정리 안 된 상태)
- 최종 리포트: `app/rag/graph_flow.py`의 `node_synthesize`

## 4. 결론 — 왜 KG 이점이 발생하지 않았나

기술 선택은 타당했습니다. 문제는 **부품 사이가 연결되지 않은 것**입니다.

```
규모를 의도적으로 억제하여 그래프가 5건 규모에 머물렀고
정규화가 없어 그 5건조차 44조각으로 쪼개졌고
Neo4j는 경로 밖에 있었고
그래프 결과는 최종 리포트에 문자열로 덧붙여졌다

→ 지식그래프의 이점이 발생할 조건 자체가 갖춰지지 않았다
```

이것은 실험으로 답할 문제가 아니라 구조로 이미 확인된 사실입니다.

## 6. 현재 유효한 계획

### 검증할 가설

그래프가 44조각인 원인이 둘 중 무엇인가.

```
가설 A  기사가 5건뿐이라 이어질 게 없다      → 규모 문제
가설 B  같은 대상이 다른 이름으로 저장됐다   → 정규화 문제
```

### 측정 지점

```
v0   5건 색인, 정규화 없음       ← 이미 측정 완료 (§3 수치 사용)
v1   40건 색인, 정규화 없음      ← 기준
v2   40건 색인, 정규화 적용      ← 가설 B 검증
◆ 게이트: v1→v2 효과 크기로 v3/v4 진행 여부 결정
v3   200건 색인, 정규화 없음     ← 가설 A 검증
v4   200건 색인, 정규화 적용     ← 상호작용
```

v0→v1은 규모 축의 두 번째 관측점이 되어, 게이트 판단의 외삽 근거로 사용됩니다.

**v1→v2를 먼저 하고 게이트에서 판단합니다.** 정규화 효과가 40건에서 이미 크면 200건 수집이 결론을 바꾸지 않으므로, 크롤러 개조(2~4시간)를 하지 않습니다.

예상 상호작용: 규모가 커지면 별칭 충돌이 늘어 **정규화 효과가 규모에 따라 커질 것**. 실증되면 "데이터를 더 모으는 게 답이 아니었다"가 헤드라인이 됩니다.

### 지표 — 전부 결정론적

LLM judge, 루브릭, 블라인드 평가가 필요 없습니다. 그래프 쿼리로 나오는 숫자라 정답이 논쟁되지 않습니다.

**규모가 다른 지점을 비교하므로 절대 개수는 쓸 수 없습니다. 반드시 비율로 정의합니다.**

| 지표 | 정의 | 현재 (5건 기준) | 방향 |
|---|---|---|---|
| `components_per_doc` | 연결 컴포넌트 수 / 색인 문서 수 | 44 / 5 = 8.8 | 낮을수록 좋음 |
| `bridges_per_doc` | 브릿지 엔티티 수 / 색인 문서 수 | 3 / 5 = 0.6 | 높을수록 좋음 |
| `cross_doc_path_ratio` | 교차문서 경로 / 전체 hop≥2 경로 | 33 / 186 = 0.177 | 높을수록 좋음 |
| `rel_type_ratio` | 관계 타입 수 / 관계 수 | 16 / 18 = 0.89 | 낮을수록 좋음 |
| `parse_failure_ratio` | placeholder 노드 / 전체 노드 | 측정 필요 | 낮을수록 좋음 |
| `isolated_doc_ratio` | 고립 문서 / 색인 문서 | 2 / 5 = 0.4 | 낮을수록 좋음 |
| `entities_per_doc` | 고유 엔티티 수 / 색인 문서 수 | 134/5 = 26.8 | 코퍼스 증가 시 하락해야 정상 |

v0→v1 에서 이 값이 유지되면 엔티티 재사용이 없다는 뜻이며,
정규화 부재가 확증된다. v1→v2 정규화 효과의 예측치가 된다.

**지표 정의를 실행 후에 바꾸지 마세요.** 사후 조정이 됩니다.

### 게이트 판정 기준 (확정 — §8 미정 3 해결)

기준선: v0 = 5건, `components_per_doc` 8.8, `entities_per_doc` 26.8

이 지표는 엔티티 재사용이 없으면 문서 수와 무관하게 값이 유지된다.
5건 → 40건에서 각 기사의 상대 문서가 4개 → 39개로 약 10배 늘어나므로,
이름이 통일돼 있다면 값이 유의미하게 하락해야 한다.

**주 지표: `components_per_doc`**

| 값 | 판정 |
|---|---|
| ≥ 7.0 | 무변화. 수집 중단, 정규화로 전환 |
| 4.0 ~ 7.0 | 보류. v2 결과로 판단 |
| ≤ 4.0 | 규모 유효. 200건 수집 진행 |

**확인 지표: `entities_per_doc`**

| 값 | 판정 |
|---|---|
| ≥ 24 | 재사용 없음. 이름 문제 확정 |
| ≤ 18 | 재사용 발생 |

엇갈릴 경우 `entities_per_doc` 우선.
섬(컴포넌트) 감소 + 엔티티 유지 → 계산 오류 의심, 진행 중단.

**교란 통제**: 현재 40건은 9개 섹션에 흩어진 이틀치 일반 뉴스이므로,
이름이 통일돼도 주제 무관으로 안 붙을 수 있다.
전체 40건과 별도로 섹션별 부분집합(증권 12건, 사회 10건)에서도
같은 지표를 산출한다. 증권 12건에서도 무변화면 주제 무관 가설이
배제되고 이름 문제가 확정된다. 추가 호출 없음.

이 기준은 v1 측정 전에 확정되었으며 결과를 보고 수정하지 않는다.

### 정규화 작업 내용 (LLM 호출 0)

결정론적 후처리입니다. 추출된 트리플에 사후 적용하므로 추출을 다시 하지 않습니다.

**엔티티** — 별칭 사전 + 표기 정규화
```
이재명 · 이재명 대통령              → 이재명
삼성전자 · 삼성 · 삼성전자(005930)  → 삼성전자
```

**관계** — 한국어 활용형 정규화가 핵심
```
선고 · 선고했다 · 선고받았다  → SENTENCE (방향으로 구분)
판단 · 판단했다               → JUDGE
피해입었다 · 피해자_수         → DAMAGE
특징 · 모습                   → 제거 (무의미)
PREDICATE                     → 제거 (파싱 실패)
```

관계 온톨로지 목표 목록은 **실제 등장 빈도에서 유도**합니다. 상상해서 만들지 마세요.
버려진 트리플 비율을 로그로 남기세요. 20% 초과면 온톨로지가 너무 좁습니다.

### 200건 수집 (게이트 통과 시에만)

(참고) 40건 색인(v1)은 버그 수정이 아니라 기존 인덱싱 스크립트 재실행만으로 가능합니다 — §3 발견 1 참고.

- 크롤러(`app/etl/extractor.py`)는 BeautifulSoup 기반이므로 **진입점만 바꾸면** 과거 기사 수집 가능. 본문 파서는 재사용
- RSS 피드 → 섹션 목록 페이지 페이지네이션
- `robots.txt` 확인, 요청 간 1초 이상 지연
- **증권·기업 섹션 최근 2~3개월치**. 무작위 수집은 현재 40건과 같은 실패를 반복함 (엔티티 재등장률이 관건)
- 인수합병·규제 후속보도가 섞이면 상태 변화(검토→철회)가 잡혀 후속 작업의 재료가 됨

## 7. 절대 금지

1. **측정 전에 제거하지 않는다.** 미검증 가설로 코드를 삭제하지 말 것
2. **한 번에 하나만 바꾼다.** v1→v2에서 정규화 외의 것을 건드리면 효과가 분리되지 않음
3. **베이스라인을 덮어쓰지 않는다.** `tests/fixtures/baseline_v*.json`은 append만
4. **지표 정의를 실행 후 변경하지 않는다**
5. **범위 밖 리팩토링 금지.** 발견 사항은 `docs/found-issues.md`에 기록만 하고 고치지 말 것
6. **ETL/DAG를 임의로 실행하지 않는다.** 색인은 명시적 지시가 있을 때만
7. **`docs/archive/` 를 참조하지 않는다.** 폐기된 설계
8. **미정 사항을 임의로 정하지 않는다.** §8 참조. 물어볼 것
